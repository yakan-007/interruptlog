# 日報出力 設計案

作成日: 2026-11-17 / 状態: 設計案（未実装・コード変更なし）

InterruptLog の日報印刷と日報プロフィールを、「削る」から「日報として満足できるものに作り直す」へ方針転換するための調査と設計案。

前提（この設計で使わないもの）: 緊急度（`urgency`）、「この件をタスクにする」（`interruptOriginId` 由来の後追い作業）、休憩の目安時間（`breakDurationMinutes` / `defaultDurationMinutes`）、アクセントカラー。これらは削除予定なので、日報の項目にも計算にも使わない。

---

## 1. 調査: 日本の職場の日報

### 1.1 一般的な構成

ビジネス向けの解説記事（マネーフォワード、カオナビなど）で共通して挙がる項目は次のとおり。会社・職種で差はあるが、骨格はほぼ同じ。

| 項目 | 内容 | 典型的な分量 |
| --- | --- | --- |
| 日付・所属・氏名 | 誰の何日の日報か | 1 行 |
| 本日の目標・予定 | 朝の時点での計画 | 1〜3 行 |
| 業務内容（実績） | やったこと。時間記録が必要な職場では業務ごとの開始〜終了時刻や所要時間 | 箇条書き |
| 成果・進捗 | 完了したもの、どこまで進んだか、目標の達成度 | 1〜3 行 |
| 課題・問題点 | 詰まったこと、予定より遅れたこと、その原因 | 1〜3 行（なければ「特になし」で可） |
| 対策・改善 | 課題に対して次にどうするか | 1〜2 行 |
| 明日の予定 | 翌日やること | 箇条書き |
| 所感・気づき・連絡事項 | 上司に共有したいこと、相談 | 1〜3 行 |

振り返りフレームワークとして KPT（Keep / Problem / Try）や YWT（やったこと / わかったこと / 次やること）を日報に組み込む例も多い。KPT の解説では「予定工数と実績工数を並べて見られると、Problem を『忙しかった』ではなく『この工程が予定を超えた』と具体的に書ける」と指摘されている。これは InterruptLog の見積機能を残す方針（超過理由を考えるきっかけ）とそのまま重なる。

製造現場の作業日報はもう少し定型で、日付・氏名・作業区分・作業時間・数量（計画数／良品数／不良数）・異常と処置（例: 部品欠品で 20 分待ち）・停止や段取りの時間と理由・翌日の予定・連絡事項が並ぶ。読み手（班長・監督）は翌朝の段取りと工数・原価集計に使う。

### 1.2 良い日報と悪い日報の違い

調査結果と一般的な指摘を整理すると、差は次の点に出る。

| 観点 | 悪い日報 | 良い日報 |
| --- | --- | --- |
| 具体性 | 「資料作成」「打ち合わせ対応」 | 「A 社見積書 v2 作成（完了）」「B 案件の仕様確認 45 分」 |
| 事実と意見 | 混ざっている | 事実（数字・結果）と所感が分かれている |
| 予定との比較 | 実績の羅列だけ | 朝の予定・見積に対してどうだったかが書いてある |
| 課題 | 「忙しかった」「時間が足りなかった」 | 「割り込み 6 件・計 1 時間 20 分で C の着手が遅れた」のように原因が特定できる |
| 次の行動 | ない | 課題に対する対策と、明日の予定がある |
| 読み手の手間 | 長文で要点が埋もれる | 冒頭で要点が分かり、1 分で読める |
| 書き手の手間 | 毎日ゼロから書くので形骸化する | 定型部分は自動、考える部分だけ書く |

最後の行が InterruptLog の強み。悪い日報の多くは「書くのが面倒で中身が薄くなる」ことから生まれるので、事実と数字は記録から自動で埋め、本人には「なぜ」と「次どうするか」だけを書かせる構成にすれば、良い日報の条件を少ない手間で満たせる。

### 1.3 タイムトラッカー由来の日報で、読み手に価値がある情報

上司・チームが日報から知りたいのは「何が終わったか」「何が遅れていて、なぜか」「助けが要るか」「明日どうするか」。タイムトラッカーの数字は、それを裏付ける証拠として使うと価値が出る。逆に、数字を全部並べると読まれない。

価値が高い（日報の本文に載せる）:

1. **完了したタスク** と、見積があるものは **見積 → 実績**。超過したものだけ強調する。
2. **未完了で今日手を付けたタスク** の進み具合（今日の作業時間、累計、見積残）。
3. **期限が今日・過ぎた・近い（例: 3 日以内）の未完了タスク**。上司が一番知りたい「遅れそうなもの」。
4. **割り込みの要約**: 件数・合計時間・発信者別の上位、長かったものの件名。「誰から何で時間を取られたか」は上司が介入できる情報。
5. **本人が書く**: 超過・遅れの理由、所感、相談、明日の予定。

価値が中（付録・印刷の下段・CSV 向き）:

- 作業時間の合計（記録時間・タスク・割り込み・休憩）
- 時系列の作業ログ（何時から何時まで何をしていたか）
- 記録のみの作業（タスク化していない作業の内容と時間）
- 勤務時間外の作業時間（勤務時間を設定している場合）

価値が低い（日報には載せない、分析画面に任せる）:

- 時間帯別の割り込み傾向、マイクロ割り込みの統計、曜日別推移
- 割り込みのカテゴリ内訳の細かい比率

## 2. 現状の実装

### 2.1 日報印刷（`src/screens/Report/cards/printTemplate.jsx` / `src/styles/screens/report-print.css`）

- レポート画面の「日」表示でだけ描画され、通常は `display: none`。「日報出力」ボタンが `window.print()` を呼び、`@media print` で日報だけが出る。
- データは `buildDailyReportData`（`src/features/report/taskMetrics.js:125`）が作る。構成は次の順:
  1. 見出し: 「日報」、日付、所属 · 氏名、表示範囲の時刻
  2. 合計 4 つ: 記録時間 / タスク / 割り込み / 休憩
  3. 完了タスク / 未完了タスク（2 列）
  4. タスク別作業時間（上位 8 件）
  5. 記録のみの作業
  6. 割り込みの内訳（時間の長い上位 5 件。件名・発信者・カテゴリ・時間）
  7. 記録済みメモ（先頭 6 件）

現状の問題点:

| # | 問題 | 影響 |
| --- | --- | --- |
| P1 | 本人が書く欄（所感・課題・明日の予定）がない | 「時間の集計表」であって日報になっていない。結局別に日報を書くことになる |
| P2 | 見積・期限が印刷に出ない（`taskEngagement.rows` に `plannedMs` / `estimateDiffMs` はあるが未使用） | 「見積に対してなぜ超過したか」を考えるきっかけが日報に現れない |
| P3 | 完了／未完了の判定が **今の** `task.isCompleted` を使っている（`buildDailyReportData`）。`buildTaskReport` の `completedInRange` のように `completedAt` で判定していない | 過去日の日報を出すと、その日以降に完了したタスクも「完了」に入る。逆に、その日に完了して後で未完了に戻したものは消える |
| P4 | 割り込みは上位 5 件だけ、メモは先頭 6 件だけ。件数・合計は出ない | 割り込みが多かった日ほど実態が伝わらない |
| P5 | 「完了タスク」「未完了タスク」「タスク別作業時間」で同じタスクが 2 回出る | 紙面が冗長 |
| P6 | 範囲の時刻が `range.since`〜`range.until`（今日なら 0:00〜現在時刻）で、勤務時間や実際の最初・最後の記録ではない | 「0:00 - 18:42」のような意味の薄い表示になる |
| P7 | 出力手段が印刷しかない | Slack / Teams / メール / 社内の日報システムに貼るには手で書き写すしかない |

### 2.2 日報プロフィール（`reportProfile`）

- `preferences.reportProfile = { affiliation, name }`（`src/state/schema.js:30`）。設定 → 日報プロフィール（`ReportProfileSheet`, `src/screens/Settings/PersonalPanels.jsx:187`）で編集。
- 使われているのは印刷の見出しと CSV の `affiliation` / `memberName` 列だけ。
- 単体だと価値が薄いが、チーム版（Part 3）で複数人の日報を集約するときは「誰の日報か」を示す唯一の情報になるので、残す価値がある。

### 2.3 CSV（`src/state/reports.js`）

- `buildReportCsv`: 1 行 = 1 記録（イベント）。列は `reportDate, range, timezone, affiliation, memberName, start, end, type, label, category, categoryId, taskId, sourceTaskId, interruptOriginId, who, urgency, memo, durationMinutes`。
- `buildAnalysisCsv`: 上記に連続性の分析列（前後のイベント種別、間隔、マイクロイベント判定など）を追加したもの。
- どちらも「生データの書き出し」で、日報の要約（完了タスク、見積差、本人の記入）は入っていない。`urgency` / `interruptOriginId` は削除予定の機能の列。
- `start` / `end` は ISO 8601（UTC）なので、Excel でそのまま開くと日本時間にならない。

## 3. 設計案

### 3.1 方針

1. **日報データを 1 つ作り、出力形式はその見せ方を変えるだけにする。** 純粋関数 `buildDailyReport(state, dayStart, now)` が `DailyReport` オブジェクトを返し、印刷・コピー用テキスト・CSV・（将来の）チーム版 JSON はすべてそれを描画する。現状は印刷と CSV が別々にデータを組み立てている。
2. **自動で埋まる「事実」と、本人が書く「考え」を分ける。** 事実は記録から必ず埋め、本人が書く欄は少なく（3〜4 欄）、空でも出力できるようにする。
3. **見積・期限は「考えるきっかけ」として出す。** 超過したタスク・期限が迫るタスクの横に、本人が理由を書ける場所を置く。数字で責める表示（赤字の大きな「+120%」など）にはしない。
4. **読み手が 1 分で読める順に並べる。** 要約 → 完了 → 進行中・遅れ → 割り込み → 所感・明日 → 付録（時系列ログ）。

### 3.2 日報の構成（項目一覧）

凡例: **自動** = 記録から埋まる / **書く** = 本人が書く / **自動+書く** = 下書きを自動で作り、本人が直せる

| # | セクション | 中身 | 区分 | データ元 |
| --- | --- | --- | --- | --- |
| 0 | 見出し | 日付（曜日つき）、所属・氏名、勤務時間（設定時）または最初〜最後の記録時刻 | 自動 | `reportProfile`、`workSchedule` / `workdaySchedules`、イベントの最小 start・最大 end |
| 1 | 今日のまとめ | 記録時間・タスク時間・割り込み（件数と時間）・休憩、完了 n 件 | 自動 | `calculateRangeStats` |
| 2 | ひとこと要約 | 今日の要点を 1〜2 行 | 書く | 新規 |
| 3 | 完了したタスク | タスク名、カテゴリ、今日の作業時間、**見積 → 累計実績**（見積があるとき）、超過時は理由欄 | 自動+書く（理由） | `tasks`（`completedAt` が当日）、`planning.plannedDurationMinutes`、タスクの全期間累計 |
| 4 | 進行中のタスク | 今日手を付けた未完了タスク。今日の作業時間、累計／見積、**期限**（今日・超過・3 日以内を強調）、遅れ・超過の理由欄 | 自動+書く（理由） | `tasks`、`planning.dueAt` |
| 5 | 記録のみの作業 | タスクにしていない作業の内容（`workDetail`）と時間 | 自動 | `events`（`type: task` かつ `taskId` なし） |
| 6 | 割り込み | 合計の件数・時間、発信者別の上位（件数・時間）、時間の長かったもの上位（件名・発信者・時間・メモ） | 自動 | `events`（`type: interrupt`）の `label` / `who` / `memo` / `categoryId` |
| 7 | 課題・相談 | 困っていること、上司に判断してほしいこと | 書く | 新規 |
| 8 | 明日の予定 | 未完了タスクから下書き（期限が近い順 → 並び順）。本人が並べ替え・削除・追記 | 自動+書く | `tasks`（未完了、`order`、`dueAt`） |
| 9 | 所感・連絡事項 | 気づき、共有したいこと | 書く | 新規 |
| 付録 | 時系列ログ | 開始〜終了・種別・内容・時間の一覧 | 自動 | `events` |

自動の補足:

- **完了の判定**は `task.completedAt` が当日の範囲に入るかで行う（P3 の修正）。過去日の日報でも当時の状態が出る。
- **見積との差**は「累計実績 − 見積」。累計は全期間（`allTime`）で、当日分ではない。表示は「見積 2h → 実績 3h10m（+1h10m）」程度に抑える。超過したタスクだけ理由欄を出す。
- **期限**は日付のみ表示（「11/18 期限」「期限 2 日超過」）。完了済みで期限を過ぎて完了したものは「期限 11/15 → 11/17 完了」と出す。
- **割り込みの要約**は件数と合計を必ず出し、明細は上位 5 件＋「ほか n 件 / m 分」とする（P4 の修正）。メモは明細の行に添える。
- 割り込みの発信者は個人名が入りうる。チーム版や社外への共有を考えると、発信者を出すかどうかは出力時に切り替えられると良い（判断事項 D6）。
- **休憩**は合計時間だけ。内訳（昼食・私用）は出さない（私用の中身を日報に出す理由がない）。

### 3.3 本人が書く欄

| 欄 | 用途 | 推奨 |
| --- | --- | --- |
| ひとこと要約 | 読み手が最初に見る 1〜2 行 | 任意。空なら出力から省く |
| タスクごとの理由（超過・遅れ） | 見積・期限に対する振り返り | 超過・期限超過のタスクにだけ欄を出す。任意 |
| 課題・相談 | 上司のアクションが要ること | 任意。空なら「特になし」と出すか省くかは設定 |
| 明日の予定 | 自動下書きを直す | 下書きをそのまま使えば書く手間ゼロ |
| 所感・連絡事項 | 自由記述 | 任意 |

KPT / YWT の欄名にはしない。日本の職場で最も通じる「課題」「明日の予定」「所感」の語を使い、KPT 的な考え方（Problem → Try）は「理由」と「明日の予定」で自然に書ける形にする。

保存先の案（判断事項 D2）:

```js
// state に追加する案
dailyNotes: {
  '2026-11-17': {
    summary: '',          // ひとこと要約
    issues: '',           // 課題・相談
    tomorrow: [           // 明日の予定（下書きを確定したもの）
      { taskId: 't1', text: '' },     // タスク由来
      { taskId: null, text: '○○に電話' }, // 手入力
    ],
    remarks: '',          // 所感・連絡事項
    taskReasons: { 't1': '仕様変更で再作業' }, // タスクごとの理由
    updatedAt: 0,
  },
}
```

- localStorage のみ・サーバーなしの前提で、バックアップ（JSON）に含め、`normalizeState` で正規化する。
- タスクごとの理由は `task.memo` に書き込まない。メモはタスクの説明として使われており、日付ごとの振り返りとは寿命が違う。
- 記入はレポート画面の「日」表示に「日報を書く」シート（またはカード）を置き、そこから印刷・コピーする流れが自然。終業時に 1 画面で完結させる。

### 3.4 出力形式ごとの向き不向き

| 形式 | 向いている用途 | 向いていない用途 | この設計での役割 |
| --- | --- | --- | --- |
| **コピーして貼る文章（プレーンテキスト）** | Slack / Teams / メール / 社内日報システムへの貼り付け。PC で働く人の日報提出の大半はこれ | 表の見た目、数字の再集計 | **主役にする。** 最も使われる。見出しは【】、箇条書きは「・」で、Markdown を解釈しない貼り付け先でも崩れない形にする |
| **コピー（Markdown）** | Slack・Notion・GitHub など Markdown を解釈する場所 | メール、Excel | テキストの切り替えオプション。必須ではない（判断事項 D4） |
| **印刷・PDF** | 紙で提出する職場、ファイルで残す・添付する、上司が紙で押印する運用 | 毎日の提出（手間）、数字の再利用 | 書式を整えた 1 枚（A4 縦）。本人の記入欄が空のときは「手書き用の罫線枠」を出すと、印刷して手書きする運用にも対応できる（判断事項 D5） |
| **CSV（要約）** | Excel での集計、月次の工数集計、チーム版への受け渡し | 人が読む日報 | 1 行 = 1 タスク（＋記録のみ作業・割り込み）の「日報明細」を新設する案。見積・実績・期限・理由を列で持つ |
| **CSV（生データ）** | 分析、他ツールへの移行 | 日報 | 現行 `buildReportCsv` を残す。`urgency` / `interruptOriginId` 列は削除、時刻はローカル時刻列を追加 |
| **Excel に貼れる表（TSV をクリップボードへ）** | 職場の既存 Excel 日報への転記（Part 3 の「メモ紙 → Excel 手打ち」の置き換え） | 文章としての日報 | 将来。職場の Excel の列構成を確認してから（Part 3 の「最初の一歩」） |
| **日報 JSON（1 日分）** | チーム版の集約ビューアへの受け渡し | 人が読む | 将来。`DailyReport` オブジェクトをそのまま書き出せば済むように、今の段階でデータ構造を決めておく |

### 3.5 印刷レイアウト（A4 縦 1 枚）

上から: 見出し（日付・所属氏名・勤務時間）→ 合計の帯 → 要約 → 完了 / 進行中（表: タスク・今日・累計/見積・期限・理由）→ 割り込み（合計と上位）→ 課題・相談 / 明日の予定（2 列）→ 所感 → 付録の時系列ログ（2 枚目に回してよい）。

- 本人の記入欄が空なら、罫線つきの空欄を出す（手書き運用への対応）。
- 印刷用 CSS は現行 `report-print.css` を作り直す。色は使わず、超過・期限は記号（⚠ / +）と太字で示す。

### 3.6 日報プロフィール

- 現行の「所属」「氏名」は残す。チーム版で人を識別する唯一の情報になる。
- 追加候補（判断事項 D7）: 「日報の宛先・見出し」（例: 「業務日報」「作業日報」）、出力に含める項目の既定（発信者を出す・時系列ログを付ける・空欄を省く）。
- 設定画面の奥ではなく、日報シートの中から編集できると、初回の日報作成時に自然に埋まる。

### 3.7 実装の見通し（参考）

1. `buildDailyReport(state, dayStart, now)` を `src/features/report/` に新設し、P3（完了判定）・P4（件数の切り捨て）・P6（時刻範囲）を直したデータを返す。テストを先に書く。
2. `dailyNotes` を schema / バックアップ / 正規化に追加。
3. 日報シート（記入 UI）＋「コピー」ボタン（`navigator.clipboard.writeText`）。
4. 印刷テンプレートと CSS を `DailyReport` から描画するように作り直す。
5. CSV の整理（日報明細 CSV の追加、生データ CSV から削除予定列を外す）。

各段階で単体で出荷できる。最初の 1〜3 だけでも「コピーして貼れる日報」が完成する。

## 4. 実装前にユーザーが判断すべき点

| # | 判断事項 | 選択肢 | 推奨 |
| --- | --- | --- | --- |
| D1 | 日報の主な出力先はどれか | (a) コピーして貼る文章 (b) 印刷・PDF (c) 両方同格 | (a) を主役、(b) は整えた補助。PC で働く人の提出先はチャット・メール・社内システムが多いため |
| D2 | 本人が書く欄を持つか、持つならどこに保存するか | (a) `dailyNotes` を state に追加して保存・バックアップ対象 (b) 保存せず、出力時にその場で書くだけ (c) 書く欄は持たず、コピー後に貼り付け先で書いてもらう | (a)。後から日報を見返せる・再出力できる。チーム版 JSON にも載る |
| D3 | 本人が書く欄の数と名前 | 案: ひとこと要約 / タスクごとの理由 / 課題・相談 / 明日の予定 / 所感・連絡事項 | 5 つで開始し、使わない欄は空なら出力から省く。欄の名前を利用者が変えられるようにするかは保留 |
| D4 | コピー形式 | (a) プレーンテキストのみ (b) プレーンテキスト＋Markdown 切り替え | (a) から始める。Markdown は要望が出てから |
| D5 | 印刷で記入欄が空のとき | (a) 欄ごと省く (b) 手書き用の罫線枠を出す | 職場の運用次第。紙に手書きで追記して提出する人がいるなら (b) |
| D6 | 割り込みの発信者名を日報に出すか | (a) 常に出す (b) 出力時に切り替え (c) 出さない | (b)。上司向けには有用だが、社外・チーム共有では個人名の扱いに配慮が要る |
| D7 | 日報プロフィールに足すもの | 見出し名（業務日報／作業日報）、項目の表示既定 | 見出し名だけ追加。項目の既定は D6 の切り替えで足りる |
| D8 | 「明日の予定」の下書きの作り方 | (a) 期限が近い未完了タスク (b) 今日触った未完了タスク (c) タスク一覧の上から n 件 | (a)＋(b) を期限順、なければ並び順。本人が直す前提 |
| D9 | 見積超過の扱い | 超過したタスクにだけ理由欄を出す／すべてのタスクに出す／しきい値（例: +20% 以上）で出す | 超過したものだけ。しきい値は設けず、理由は任意 |
| D10 | 日の区切り | (a) 暦日 0:00〜24:00（現行） (b) 勤務時間の設定に合わせる | (a) のまま。夜勤など日をまたぐ勤務への対応はチーム版で再検討 |
| D11 | CSV の整理 | 日報明細 CSV を新設するか／生データ CSV の `urgency`・`interruptOriginId` 列を削るか／時刻をローカル時刻にするか | 3 つとも実施。ただし列の削除は既存 CSV を取り込んでいる人がいるなら告知が要る |
| D12 | 分析用 CSV（`buildAnalysisCsv`）を残すか | 残す／日報作り直しを機に削る | 「基本はタイマー」の方針なら削除候補。日報とは独立に判断してよい |
| D13 | チーム版を見越した日報 JSON 出力を今作るか | 今作る／データ構造だけ決めて後回し | 後回し。`DailyReport` の形を決めておけば後から足せる |
