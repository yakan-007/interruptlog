# 日報出力 設計案

作成日: 2026-11-17 / 改訂: 2026-11-18 / 状態: 設計案（未実装・コード変更なし）

改訂メモ（2026-11-18）: 「本人が終業時に書く欄」をアプリ内に作らない方針に変更した。日報は記録から自動で作る事実だけにし、本人のコメントは貼り付け先（チャット・メール）で書き足すか、印刷した紙に手で書く。「なぜ」は作業中のメモ（割り込みのメモ・作業メモ）で拾う。

InterruptLog の日報印刷と日報プロフィールを、「削る」から「日報として満足できるものに作り直す」へ方針転換するための調査と設計案。

前提（この設計で使わないもの）: 緊急度（`urgency`）、「この件をタスクにする」（`interruptOriginId` 由来の後追い作業）、休憩の目安時間（`breakDurationMinutes` / `defaultDurationMinutes`）、アクセントカラー。これらは削除予定なので、日報の項目にも計算にも使わない。

## 1. 調査: 日本の職場の日報

### 1.1 一般的な構成

ビジネス向けの解説記事（マネーフォワード、カオナビなど）で共通して挙がる項目は次のとおり。会社・職種で差はあるが、骨格はほぼ同じ。

| 項目 | 内容 | 典型的な分量 |
| --- | --- | --- |
| 日付・所属・氏名 | 誰の何日の日報か | 1 行 |
| 本日の目標・予定 | 朝の時点での計画 | 1〜3 行 |
| 業務内容（実績） | やったこと。時間記録が必要な職場では業務ごとの開始〜終了時刻や所要時間 | 箇条書き |
| 成果・進捗 | 完了したもの、どこまで進んだか、目標の達成度 | 1〜3 行 |
| 課題・問題点 | 詰まったこと、予定より遅れたこと、その原因 | 1〜3 行（なければ「特になし」で可） |
| 対策・改善 | 課題に対して次にどうするか | 1〜2 行 |
| 明日の予定 | 翌日やること | 箇条書き |
| 所感・気づき・連絡事項 | 上司に共有したいこと、相談 | 1〜3 行 |

振り返りフレームワークとして KPT（Keep / Problem / Try）や YWT（やったこと / わかったこと / 次やること）を日報に組み込む例も多い。KPT の解説では「予定工数と実績工数を並べて見られると、Problem を『忙しかった』ではなく『この工程が予定を超えた』と具体的に書ける」と指摘されている。これは InterruptLog の見積機能を残す方針（超過理由を考えるきっかけ）とそのまま重なる。

製造現場の作業日報はもう少し定型で、日付・氏名・作業区分・作業時間・数量（計画数／良品数／不良数）・異常と処置（例: 部品欠品で 20 分待ち）・停止や段取りの時間と理由・翌日の予定・連絡事項が並ぶ。読み手（班長・監督）は翌朝の段取りと工数・原価集計に使う。

### 1.2 良い日報と悪い日報の違い

調査結果と一般的な指摘を整理すると、差は次の点に出る。

| 観点 | 悪い日報 | 良い日報 |
| --- | --- | --- |
| 具体性 | 「資料作成」「打ち合わせ対応」 | 「A 社見積書 v2 作成（完了）」「B 案件の仕様確認 45 分」 |
| 事実と意見 | 混ざっている | 事実（数字・結果）と所感が分かれている |
| 予定との比較 | 実績の羅列だけ | 朝の予定・見積に対してどうだったかが書いてある |
| 課題 | 「忙しかった」「時間が足りなかった」 | 「割り込み 6 件・計 1 時間 20 分で C の着手が遅れた」のように原因が特定できる |
| 次の行動 | ない | 課題に対する対策と、明日の予定がある |
| 読み手の手間 | 長文で要点が埋もれる | 冒頭で要点が分かり、1 分で読める |
| 書き手の手間 | 毎日ゼロから書くので形骸化する | 定型部分は自動、考える部分だけ書く |

最後の行が InterruptLog の強み。悪い日報の多くは「書くのが面倒で中身が薄くなる」ことから生まれる。事実と数字は記録から自動で埋まり、「なぜ」の多くは作業中のメモ（割り込みの件名・メモ、作業メモ）にすでに書かれている。日報はそれを漏れなく拾って並べればよく、終業時に思い出して書かせる必要はない。本人のコメント（相談・所感）は貼り付け先で 1〜2 行足せば足りる。

### 1.3 タイムトラッカー由来の日報で、読み手に価値がある情報

上司・チームが日報から知りたいのは「何が終わったか」「何が遅れていて、なぜか」「助けが要るか」「明日どうするか」。タイムトラッカーの数字は、それを裏付ける証拠として使うと価値が出る。逆に、数字を全部並べると読まれない。

価値が高い（日報の本文に載せる）:

1. **完了したタスク** と、見積があるものは **見積 → 実績**。超過したものだけ強調する。
2. **未完了で今日手を付けたタスク** の進み具合（今日の作業時間、累計、見積残）。
3. **期限が今日・過ぎた・近い（例: 3 日以内）の未完了タスク**。上司が一番知りたい「遅れそうなもの」。
4. **割り込みの要約**: 件数・合計時間・発信者別の上位、長かったものの件名。「誰から何で時間を取られたか」は上司が介入できる情報。
5. **作業中に書いたメモ**: 割り込みや作業のメモを、該当する行に添えて出す。超過・遅れの理由になっていることが多い。
6. **残っているタスク**: 期限が近い順。「明日の予定」の代わりになる。

本人の相談・所感は価値が高いが、アプリの外（貼り付け先・印刷した紙）で書いてもらう。

価値が中（付録・印刷の下段・CSV 向き）:

- 作業時間の合計（記録時間・タスク・割り込み・休憩）
- 時系列の作業ログ（何時から何時まで何をしていたか）
- 記録のみの作業（タスク化していない作業の内容と時間）
- 勤務時間外の作業時間（勤務時間を設定している場合）

価値が低い（日報には載せない、分析画面に任せる）:

- 時間帯別の割り込み傾向、マイクロ割り込みの統計、曜日別推移
- 割り込みのカテゴリ内訳の細かい比率

## 2. 現状の実装

### 2.1 日報印刷（`src/screens/Report/cards/printTemplate.jsx` / `src/styles/screens/report-print.css`）

- レポート画面の「日」表示でだけ描画され、通常は `display: none`。「日報出力」ボタンが `window.print()` を呼び、`@media print` で日報だけが出る。
- データは `buildDailyReportData`（`src/features/report/taskMetrics.js:125`）が作る。構成は次の順:
  1. 見出し: 「日報」、日付、所属 · 氏名、表示範囲の時刻
  2. 合計 4 つ: 記録時間 / タスク / 割り込み / 休憩
  3. 完了タスク / 未完了タスク（2 列）
  4. タスク別作業時間（上位 8 件）
  5. 記録のみの作業
  6. 割り込みの内訳（時間の長い上位 5 件。件名・発信者・カテゴリ・時間）
  7. 記録済みメモ（先頭 6 件）

現状の問題点:

| # | 問題 | 影響 |
| --- | --- | --- |
| P1 | 記録時のメモがタスク・割り込みの行と切り離され、先頭 6 件だけ出る。残っているタスク（明日以降の予定）も出ない | 「なぜ」と「次」が伝わらず、時間の集計表に留まる |
| P2 | 見積・期限が印刷に出ない（`taskEngagement.rows` に `plannedMs` / `estimateDiffMs` はあるが未使用） | 「見積に対してなぜ超過したか」を考えるきっかけが日報に現れない |
| P3 | 完了／未完了の判定が **今の** `task.isCompleted` を使っている（`buildDailyReportData`）。`buildTaskReport` の `completedInRange` のように `completedAt` で判定していない | 過去日の日報を出すと、その日以降に完了したタスクも「完了」に入る。逆に、その日に完了して後で未完了に戻したものは消える |
| P4 | 割り込みは上位 5 件だけ、メモは先頭 6 件だけ。件数・合計は出ない | 割り込みが多かった日ほど実態が伝わらない |
| P5 | 「完了タスク」「未完了タスク」「タスク別作業時間」で同じタスクが 2 回出る | 紙面が冗長 |
| P6 | 範囲の時刻が `range.since`〜`range.until`（今日なら 0:00〜現在時刻）で、勤務時間や実際の最初・最後の記録ではない | 「0:00 - 18:42」のような意味の薄い表示になる |
| P7 | 出力手段が印刷しかない | Slack / Teams / メール / 社内の日報システムに貼るには手で書き写すしかない |

### 2.2 日報プロフィール（`reportProfile`）

- `preferences.reportProfile = { affiliation, name }`（`src/state/schema.js:30`）。設定 → 日報プロフィール（`ReportProfileSheet`, `src/screens/Settings/PersonalPanels.jsx:187`）で編集。
- 使われているのは印刷の見出しと CSV の `affiliation` / `memberName` 列だけ。
- 単体だと価値が薄いが、チーム版（Part 3）で複数人の日報を集約するときは「誰の日報か」を示す唯一の情報になるので、残す価値がある。

### 2.3 CSV（`src/state/reports.js`）

- `buildReportCsv`: 1 行 = 1 記録（イベント）。列は `reportDate, range, timezone, affiliation, memberName, start, end, type, label, category, categoryId, taskId, sourceTaskId, interruptOriginId, who, urgency, memo, durationMinutes`。
- `buildAnalysisCsv`: 上記に連続性の分析列（前後のイベント種別、間隔、マイクロイベント判定など）を追加したもの。
- どちらも「生データの書き出し」で、日報の要約（完了タスク、見積差、本人の記入）は入っていない。`urgency` / `interruptOriginId` は削除予定の機能の列。
- `start` / `end` は ISO 8601（UTC）なので、Excel でそのまま開くと日本時間にならない。

## 3. 設計案

### 3.1 方針

1. **日報データを 1 つ作り、出力形式はその見せ方を変えるだけにする。** 純粋関数 `buildDailyReport(state, dayStart, now)` が `DailyReport` オブジェクトを返し、印刷・コピー用テキスト・CSV・（将来の）チーム版 JSON はすべてそれを描画する。現状は印刷と CSV が別々にデータを組み立てている。
2. **日報は記録から作る事実だけにする。終業時に書く欄はアプリに作らない。** 本人のコメントは貼り付け先で書き足すか、印刷した紙に手で書く。アプリ内の記入欄は、保存先・バックアップ・正規化・入力画面が要り、「基本はタイマー」の方針と逆行する。
3. **「なぜ」は作業中のメモから拾う。** 割り込みの件名・メモ、作業メモを該当する行に添えて出す。その場で書いたメモは、終業時に思い出して書くより正確。
4. **見積・期限は「考えるきっかけ」として出す。** 超過したタスク・期限が迫るタスクを目立つ位置に出す。理由は書かせないが、本人が貼り付け先で書き足す材料にはなる。数字で責める表示（赤字の大きな「+120%」など）にはしない。
5. **読み手が 1 分で読める順に並べる。** まとめ → 完了 → 進行中・遅れ → 割り込み → 残っているタスク → 付録（時系列ログ）。

### 3.2 日報の構成（項目一覧）

すべて記録から自動で埋まる。本人が書く欄はない。

| # | セクション | 中身 | データ元 |
| --- | --- | --- | --- |
| 0 | 見出し | 日付（曜日つき）、所属・氏名、勤務時間（設定時）または最初〜最後の記録時刻 | `reportProfile`、`workSchedule` / `workdaySchedules`、イベントの最小 start・最大 end |
| 1 | 今日のまとめ | 記録時間・タスク時間・割り込み（件数と時間）・休憩、完了 n 件 | `calculateRangeStats` |
| 2 | 完了したタスク | タスク名、カテゴリ、今日の作業時間、**見積 → 累計実績**（見積があるとき）、その日のメモ | `tasks`（`completedAt` が当日）、`planning.plannedDurationMinutes`、タスクの全期間累計、`events.memo` |
| 3 | 進行中のタスク | 今日手を付けた未完了タスク。今日の作業時間、累計／見積、**期限**（今日・超過・3 日以内を強調）、その日のメモ | `tasks`、`planning.dueAt`、`events.memo` |
| 4 | 記録のみの作業 | タスクにしていない作業の内容（`workDetail`）・時間・メモ | `events`（`type: task` かつ `taskId` なし） |
| 5 | 割り込み | 合計の件数・時間、発信者別の上位（件数・時間）、時間の長かったもの上位（件名・発信者・時間・メモ） | `events`（`type: interrupt`）の `label` / `who` / `memo` / `categoryId` |
| 6 | 残っているタスク | 今日手を付けていない未完了タスクのうち、期限が近いもの（期限順、上限あり） | `tasks`（未完了、`dueAt`、`order`） |
| 付録 | 時系列ログ | 開始〜終了・種別・内容・時間・メモの一覧 | `events` |

「残っているタスク」は「明日の予定」とは呼ばない。本人が選んだ予定ではなく、記録から見える事実（残件と期限）として出す。進行中のタスク（#3）と合わせれば、読み手には「明日何をしそうか」が十分伝わる。

自動の補足:

- **完了の判定**は `task.completedAt` が当日の範囲に入るかで行う（P3 の修正）。過去日の日報でも当時の状態が出る。
- **見積との差**は「累計実績 − 見積」。累計は全期間（`allTime`）で、当日分ではない。表示は「見積 2h → 実績 3h10m（+1h10m）」程度に抑える。超過したタスクは同じセクションの先頭に寄せる。
- **メモ**は、そのタスク・作業・割り込みの行の下に添える（例: `└ メモ: 単価表の改定が途中で入り再計算`）。同じタスクに複数のメモがあれば時刻順にすべて出す。現行の「記録済みメモ」セクション（先頭 6 件）は廃止する。
- **期限**は日付のみ表示（「11/18 期限」「期限 2 日超過」）。完了済みで期限を過ぎて完了したものは「期限 11/15 → 11/17 完了」と出す。
- **割り込みの要約**は件数と合計を必ず出し、明細は上位 5 件＋「ほか n 件 / m 分」とする（P4 の修正）。メモは明細の行に添える。
- 割り込みの発信者は個人名が入りうる。チーム版や社外への共有を考えると、発信者を出すかどうかは出力時に切り替えられると良い（判断事項 D2）。
- **休憩**は合計時間だけ。内訳（昼食・私用）は出さない（私用の中身を日報に出す理由がない）。

### 3.3 本人のコメントの扱い（アプリでは書かせない）

本人の相談・所感・超過の理由は、読み手にとって価値が高い。それでもアプリ内に記入欄は作らず、次のように扱う。

| 場面 | 本人のコメントの書き場所 |
| --- | --- |
| 作業中 | 割り込みのメモ・作業メモ（既存機能）。日報では該当する行に添えて出る |
| コピーして貼る | 貼り付け先（Slack / Teams / メール / 社内日報システム）で、末尾に 1〜2 行書き足す |
| 印刷 | 紙面の最後に「所感・連絡事項」の罫線枠（空欄）を常に出し、手で書く |

アプリ内に記入欄を作らない理由:

- 貼り付け先でも書けるので、アプリ側に欄を作っても二度手間は減らない。
- 作ると保存先（state の新しい項目）、バックアップへの組み込み、正規化、入力画面が要る。機能を削っている「基本はタイマー」の方針と逆行する。
- 終業時の文章入力は定着しにくい。チーム版（現場の作業者がスマホで記録）ではなおさら。
- 「なぜ」の多くは作業中のメモにすでに書かれていて、そのほうが正確。

再検討する条件: 使ってみて、毎日貼り付け先で同じ種類のことを打っていると感じたら、その欄だけを足す。そのときの保存先は state の日付別の項目（例: `dailyNotes['2026-11-18']`）とし、バックアップに含める。`task.memo` には書き込まない（タスクの説明と日付ごとの振り返りは寿命が違う）。

### 3.4 出力形式ごとの向き不向き

| 形式 | 向いている用途 | 向いていない用途 | この設計での役割 |
| --- | --- | --- | --- |
| **コピーして貼る文章（プレーンテキスト）** | Slack / Teams / メール / 社内日報システムへの貼り付け。PC で働く人の日報提出の大半はこれ。本人のコメントを貼り付け先で足せる | 表の見た目、数字の再集計 | **主役にする。** 最も使われる。見出しは【】、箇条書きは「・」で、Markdown を解釈しない貼り付け先でも崩れない形にする |
| **コピー（Markdown）** | Slack・Notion・GitHub など Markdown を解釈する場所 | メール、Excel | テキストの切り替えオプション。必須ではない（判断事項 D4） |
| **印刷・PDF** | 紙で提出する職場、ファイルで残す・添付する、上司が紙で押印する運用 | 毎日の提出（手間）、数字の再利用 | 書式を整えた 1 枚（A4 縦）。最後に「所感・連絡事項」の手書き用の罫線枠を出す（判断事項 D3） |
| **CSV（要約）** | Excel での集計、月次の工数集計、チーム版への受け渡し | 人が読む日報 | 1 行 = 1 タスク（＋記録のみ作業・割り込み）の「日報明細」を新設する案。見積・実績・期限・その日のメモを列で持つ |
| **CSV（生データ）** | 分析、他ツールへの移行 | 日報 | 現行 `buildReportCsv` を残す。`urgency` / `interruptOriginId` 列は削除、時刻はローカル時刻列を追加 |
| **Excel に貼れる表（TSV をクリップボードへ）** | 職場の既存 Excel 日報への転記（Part 3 の「メモ紙 → Excel 手打ち」の置き換え） | 文章としての日報 | 将来。職場の Excel の列構成を確認してから（Part 3 の「最初の一歩」） |
| **日報 JSON（1 日分）** | チーム版の集約ビューアへの受け渡し | 人が読む | 将来。`DailyReport` オブジェクトをそのまま書き出せば済むように、今の段階でデータ構造を決めておく |

コピー用テキストの出力イメージ:

```text
【日報】2026/11/17（火） 開発チーム 山田
勤務 9:00〜18:00 ／ 記録 7h40m（タスク 5h50m・割り込み 1h20m／6件・休憩 30m）

■ 完了
・A社 見積書 v2（開発） 今日 2h10m ／ 見積 2h → 実績 3h10m（+1h10m）
　└ メモ: 単価表の改定が途中で入り再計算
・週次レポート（ドキュメント） 今日 40m

■ 進行中
・B案件 仕様書（開発） 今日 2h20m ／ 累計 4h / 見積 6h ／ 期限 11/19

■ 記録のみの作業
・社内問い合わせ対応 30m

■ 割り込み 6件 1h20m
・佐藤さん 3件 50m ／ 鈴木さん 2件 20m ／ ほか 1件 10m
・B案件 仕様の確認（佐藤さん） 35m
　└ メモ: 画面遷移の認識違い

■ 残っているタスク
・C 画面改修 期限 11/18 ⚠
・D 帳票修正 期限 11/20
```

本人は貼り付け先で、この下に「C の期限が厳しいので優先度の確認をお願いします」のように書き足す。

### 3.5 印刷レイアウト（A4 縦 1 枚）

上から: 見出し（日付・所属氏名・勤務時間）→ 合計の帯 → 完了 / 進行中（表: タスク・今日・累計/見積・期限、メモは行の下）→ 割り込み（合計と上位）→ 残っているタスク → 所感・連絡事項（罫線つきの空欄）→ 付録の時系列ログ（2 枚目に回してよい）。

- 所感・連絡事項の罫線枠は手書き用。紙で提出する職場、上司が紙に押印する運用に対応する。
- 印刷用 CSS は現行 `report-print.css` を作り直す。色は使わず、超過・期限は記号（⚠ / +）と太字で示す。

### 3.6 日報プロフィール

- 現行の「所属」「氏名」は残す。チーム版で人を識別する唯一の情報になる。
- 追加候補（判断事項 D5）: 日報の見出し名（例: 「業務日報」「作業日報」）、出力に含める項目の既定（発信者を出す・時系列ログを付ける）。
- 設定画面の奥ではなく、日報出力の画面（コピー・印刷ボタンの近く）から編集できると、初回の出力時に自然に埋まる。

### 3.7 実装の見通し（参考）

1. `buildDailyReport(state, dayStart, now)` を `src/features/report/` に新設し、P1（メモを行に添える・残っているタスク）・P3（完了判定）・P4（件数の切り捨て）・P6（時刻範囲）を直したデータを返す。テストを先に書く。
2. レポート画面の「日」表示に「日報をコピー」ボタン（`navigator.clipboard.writeText`）を追加。
3. 印刷テンプレートと CSS を `DailyReport` から描画するように作り直す（罫線枠を含む）。
4. CSV の整理（日報明細 CSV の追加、生データ CSV から削除予定列を外す）。

state のスキーマ変更は不要。各段階で単体で出荷でき、1〜2 だけで「コピーして貼れる日報」が完成する。

## 4. 実装前にユーザーが判断すべき点

| # | 判断事項 | 選択肢 | 推奨 |
| --- | --- | --- | --- |
決定済み（2026-11-18）: 本人が終業時に書く欄はアプリに作らない（3.3）。

| # | 判断事項 | 選択肢 | 推奨 |
| --- | --- | --- | --- |
| D1 | 日報の主な出力先はどれか | (a) コピーして貼る文章 (b) 印刷・PDF (c) 両方同格 | (a) を主役、(b) は整えた補助。PC で働く人の提出先はチャット・メール・社内システムが多いうえ、貼り付け先でコメントを足せる |
| D2 | 割り込みの発信者名を日報に出すか | (a) 常に出す (b) 出力時に切り替え (c) 出さない | (b)。上司向けには有用だが、社外・チーム共有では個人名の扱いに配慮が要る |
| D3 | 印刷に手書き用の罫線枠を出すか | (a) 常に出す (b) 出さない (c) 設定で切り替え | (a)。アプリ内に記入欄がない代わりに、紙では手で書けるようにする |
| D4 | コピー形式 | (a) プレーンテキストのみ (b) プレーンテキスト＋Markdown 切り替え | (a) から始める。Markdown は要望が出てから |
| D5 | 日報プロフィールに足すもの | 見出し名（業務日報／作業日報）、項目の表示既定 | 見出し名だけ追加。項目の既定は D2 の切り替えで足りる |
| D6 | 「残っているタスク」に何を出すか | (a) 期限が近い（例: 3 日以内・超過）未完了タスクだけ (b) 期限のない未完了タスクも並び順で上位 n 件 | (a)。期限のないものまで出すとタスク一覧の写しになり、読まれない |
| D7 | 見積超過の見せ方 | (a) 超過したものを先頭に寄せ、差分を併記 (b) しきい値（例: +20% 以上）を超えたものだけ強調 | (a)。しきい値は設けない |
| D8 | 日の区切り | (a) 暦日 0:00〜24:00（現行） (b) 勤務時間の設定に合わせる | (a) のまま。夜勤など日をまたぐ勤務への対応はチーム版で再検討 |
| D9 | CSV の整理 | 日報明細 CSV を新設するか／生データ CSV の `urgency`・`interruptOriginId` 列を削るか／時刻をローカル時刻にするか | 3 つとも実施。ただし列の削除は既存 CSV を取り込んでいる人がいるなら告知が要る |
| D10 | 分析用 CSV（`buildAnalysisCsv`）を残すか | 残す／日報作り直しを機に削る | 「基本はタイマー」の方針なら削除候補。日報とは独立に判断してよい |
| D11 | チーム版を見越した日報 JSON 出力を今作るか | 今作る／データ構造だけ決めて後回し | 後回し。`DailyReport` の形を決めておけば後から足せる |
